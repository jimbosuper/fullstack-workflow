# fullstack-workflow

**一套「AI + 人」的端到端交付规范。** 它把产品、设计、架构、开发、测试、审查、运维七个角色写成可执行的岗位规则，再用**三个阶段、四道门（六个停点）**把人和 AI 的分工钉死。

**不要把它当默认 agent。** 小任务用内置的 `build`，中任务用 `plan` + `build`；这套东西是给**做项目、改数据结构、需要迁移或上线**的大任务准备的。选错了由人手动切走。

```text
10 个 skill  +  1 个主 agent + 7 个角色  +  1 份全局约束  +  2 份模板
```

仓库地址：`https://github.com/jimbosuper/fullstack-workflow.git`

---

## 零、它解决什么问题

只靠一句「帮我做个功能」，模型会一路往下猜，最后交付的东西没人敢上线。这个仓库把四个失效点各自堵住：

| 失效点 | 堵法 |
|---|---|
| 需求没问清就动手 | 产品角色必须先问，**零问询的 PRD 一律视为草稿**，不许进下游 |
| AI 自己把活干完还自己签字 | **审查必须独立上下文**，审查不给自己盖章 |
| 写完就算完成 | **审查通过才生效**。写完不算，测试通过也不算 |
| 无人值守跑一夜，早上起来全是返工 | **门必须人过**，不设「预授权批量过门」 |

三条铁律贯穿全仓：

```text
1. docs/ 是唯一状态源 —— 飞书、看板只做镜像，不得反向写状态
2. 合并与上线权在人 —— test / prod 只有人能合，AI 最高推到 dev
3. 审查是生效判定 —— 写完不算，测试通过也不算，审查通过才算
```

## 一、仓库结构与装什么

| 类型 | 数量 | 内容 | 装到哪 |
|---|---|---|---|
| skill | 10（8 个 workflow + 2 个 init） | `skills/` | `~/.agents/skills/`（`npx skills add` 自动放） |
| agent | 8（1 个主 agent + 7 个角色） | `agents/` | `~/.config/opencode/agents/`（手拷） |
| 全局常驻规则 | 1 | `templates/AGENTS.md` | `~/.config/opencode/AGENTS.md` |
| 项目级模板 | 1 | `templates/project-AGENTS.md` | 每个项目复制成 `AGENTS.md` |

```text
skills/
├─ init-environment/SKILL.md       ← 装/重装全局环境
├─ init-project/SKILL.md           ← 新仓库建骨架
├─ fullstack-workflow/             ← 编排：四道门 / 派谁（主 agent 同名）
│  ├─ SKILL.md
│  └─ references/
│     ├─ doc-templates/            ← 8 份文档模板，按 docs/ 的七个域拆
│     │  ├─ 00-readme.md           ← docs/README.md：在途需求表 + 状态定义（24 份产物之一）
│     │  ├─ 01-product.md           需求池 / BRD / MRD / PRD / 术语表
│     │  ├─ 02-design.md            设计系统 / 组件规范 / 页面规格
│     │  ├─ 03-architecture.md      系统架构 / 图示 / 状态机 / 环境规范 / 数据库设计 / ER / ADR
│     │  ├─ 04-dev.md               代码规范 / 技术方案 / 实现记录
│     │  ├─ 05-test.md              测试策略 / 测试方案 / 测试报告
│     │  ├─ 06-ops.md               服务详情 / 部署拓扑 / 运维手册 / 发布记录
│     │  └─ 07-review.md            审查清单 / 审查报告
│     ├─ questioning.md           ← 提问协议：设计树 / frontier / 每问带推荐答案
│     └─ project-layout.md         ← 项目目录树（五棵树）+ 归档与版本位置规则
├─ design-workflow/SKILL.md        ← 设计（门 1）
├─ product-workflow/SKILL.md       ← 产品（门 1）
├─ architect-workflow/SKILL.md     ← 架构（门 2A）
├─ develop-workflow/SKILL.md       ← 全栈开发（门 2A/2B）
├─ test-workflow/SKILL.md          ← 测试（门 3）
├─ ops-workflow/SKILL.md           ← 运维（门 3）
└─ review-workflow/SKILL.md        ← 审查（不设门）

agents/                            ← 1 个主 agent + 7 个 OpenCode 专用角色
├─ fullstack-workflow.md          ← 主 agent（primary）：三阶段 / 四道门 / 派七个角色
├─ product-workflow.md
├─ design-workflow.md
├─ architect-workflow.md
├─ develop-workflow.md
├─ test-workflow.md
├─ review-workflow.md
└─ ops-workflow.md

templates/
├─ AGENTS.md                       ← 全局常驻（装到 ~/.config/opencode/AGENTS.md）
└─ project-AGENTS.md               ← 项目级（init-project 用）

backup-docs/                       ← 逻辑备份：7 份单文件，便于整体通读，不装
```

**`agents/` 和 `skills/*-workflow/` 是同一份内容的两副头壳。** 正文（body）与 `description` **逐字一致**，只有 frontmatter 不同：

| | frontmatter | 用途 |
|---|---|---|
| `agents/<名>.md` | `description` / `mode` / `model` | OpenCode 装成 agent |
| `skills/<名>-workflow/SKILL.md` | `name` / `description` | 跨 agent 装的 skill |

**改规则时改一处，再同步另一处。** 主 agent 同理：`agents/fullstack-workflow.md` 与 `skills/fullstack-workflow/SKILL.md` 正文一致。

**`backup-docs/` 是「合订本」**：把散在 skill / agents / templates 里的规则拼回 7 份单文件（约 6,000 行），只为人读，不参与安装。**它和活版本必须一致**——`05` / `02` / `01` / `04` / `06` 与活版本逐字对应，`03` 对应 `init-environment` 第四节。

## 二、安装

### 2.1 装之前确认四件事

| 项 | 怎么确认 | 没有会怎样 |
|---|---|---|
| OpenCode / OpenChamber 已装 | `opencode --version` | 后面全做不了 |
| 至少一个 provider 可用 | 会话里 `/models` 能看到模型 | 角色装上了但跑不起来 |
| Git 配了真人身份 | `git config --global user.name` 有值 | 提交记录追不到人 |
| 目标项目已 `git init` | 目录里有 `.git/` | 分支、提交、审查全失效 |

缺任何一项就停下补齐，不要「装完再说」。

### 2.2 装 10 个 skill

```bash
npx skills add https://github.com/jimbosuper/fullstack-workflow.git \
  --agent opencode --global
```

**三个参数各自管什么：**

| 参数 | 全名 | 作用 | 不写会怎样 |
|---|---|---|---|
| `--agent opencode` | `-a` 是它的简写 | 装给哪个 agent 用 | 会弹交互问你要装给谁 |
| `--global` | `-g` | 装进用户目录，所有项目共用 | **默认装进当前项目** `.agents/skills/`，换个仓库就没了 |
| `--copy` | — | 复制实体文件，不建软链 | 默认建软链；跨盘或容器里软链会断 |

**`-a` 就是 `--agent` 的简写，不是「all」。** 想一次装给多个 agent 就重复写：

```bash
npx skills add https://github.com/jimbosuper/fullstack-workflow.git \
  --agent opencode --agent codex --agent zcode --global
```

**skill 跨 agent 通用；`agents/` 那 8 个是 OpenCode 专用。** 其它 agent 用 skill 版就够了。

### 2.3 装 8 个 agent（1 个主 agent + 7 个角色，OpenCode 专用）

```bash
cp agents/*.md ~/.config/opencode/agents/
```

**`agents/fullstack-workflow.md` 是主 agent（`mode: primary`），另外 7 个是 `mode: subagent`。** 装完在会话里能选到 `fullstack-workflow`，和内置的 `build`、`plan` 并列——**做项目选它，小改动用 build，中等改动用 plan**。

**装之前必须改两处，否则装上也跑不起来：**

**① `model` 一行是占位，必须换成你本机真有的模型。**

```yaml
model: <provider>/<model>#high     # ← 改这里
```

`#` 后面是推理档位（reasoning effort），可选值取决于你的模型定义。仓库里给的默认档位：

| 角色 | 默认档位 | 理由 |
|---|---|---|
| **主 agent** | `#high` | 编排者要读整套产物、判差集、决定派谁；**别降到 low** |
| 产品 | `#low` | 主要是提问与整理，不需要深推 |
| 设计 | `#high` | 要读派发指令、验收 OpenDesign 产物、校验单文件与四态 |
| 架构 | `#high` | 结构与数据模型错了下游全废 |
| 全栈开发 | `#high` | 实现 + 自测 |
| 测试 | `#low` | 按 TP 逐条跑 |
| 审查 | `#max` | 唯一的把关者，最该花算力 |
| 运维 | `#low` | 写文档、查状态 |

**② 文件名和机器上已有的旧名对不上时，先删旧文件再装。**

| 本仓库文件名 | 旧版（备份素材）用的名字 |
|---|---|
| `product-workflow.md` | `product-manager.md` |
| `design-workflow.md` | `designer.md` |
| `architect-workflow.md` | `architect.md` |
| `develop-workflow.md` | `fullstack-dev.md` |
| `test-workflow.md` | `test-runner.md` |
| `review-workflow.md` | `code-reviewer.md` |
| `ops-workflow.md` | `ops-engineer.md` |

两套并存会有 14 个角色，模型派错人。**确认旧版没用之后再删。** `mode: subagent` 那一行不能删——不写会被当成主 agent，反而抢走本该派给子代理的活。

### 2.4 装全局 AGENTS.md

```bash
cp templates/AGENTS.md ~/.config/opencode/AGENTS.md
```

**已有 `AGENTS.md` 的先看内容再决定覆盖还是合并**，直接覆盖会冲掉你自己写的规则。

**仓库里这份只装通用的地板规则**：安全底线、执行纪律、事实与表达、交付、上下文，共 9 个 `##` 节题。**三阶段、四道门、分级规则不在这里**——它们在 `agents/fullstack-workflow.md` 里，只有那个主 agent 读得到。

**如果你机器上的 AGENTS.md 写「三道门」「八道门」「任务分级」，直接 `cp` 覆盖是对的**——旧版把这些规则塞进全局，会让 `build` 修一个 bug 时也读着一整套门规则。**验一下覆盖后的节数**：

```bash
grep -c "^## " ~/.config/opencode/AGENTS.md      # 9
grep -c "任务分级" ~/.config/opencode/AGENTS.md   # 0
```

### 2.5 初始化项目（每个新仓库一次，由主 agent 自己跑）

**不要手工执行下面这些命令。** 第一次在项目里选 `fullstack-workflow` 并说要做某个需求时，它会在阶段 1 的第 0 步先加载 `init-project` skill 把骨架建好，然后再问清范围。

它做五件事：建 `docs/` 目录树、补 `.gitignore` 五条、把模板落进 `docs/99-模板文档/`、生成 `docs/07-审查/01-审查清单/01-审查清单.md`、给出项目 `AGENTS.md` 要填的字段。

**检查它有没有做**：

```bash
test -s docs/07-审查/01-审查清单/01-审查清单.md && echo OK
test "$(grep -c '^## [一二三四五六七八九]、' docs/07-审查/01-审查清单/01-审查清单.md)" = 9 \
  && grep -c '^### 4\.' docs/07-审查/01-审查清单/01-审查清单.md   # 三个阶段各一条，应为 3
```

**这份清单是 9 节，没有「按角色分组」那一节。** 角色自检照**第四节**里自己阶段那一小节（4.1 阶段 1 / 4.2 阶段 2 / 4.3 阶段 3）；审查角色另外过**第五节**「必检项（按对象类型）」。**不要另建第九节按角色分组**——同一批必检项存在两处，改一处必漏一处。

**下面这段是 `init-project` 内部逻辑的展开，供排查用，不是让你手敲的：**

```bash
mkdir -p docs/99-模板文档
cp <本仓库>/skills/fullstack-workflow/references/project-layout.md docs/99-模板文档/
cp <本仓库>/skills/fullstack-workflow/references/questioning.md docs/99-模板文档/
cp -r <本仓库>/skills/fullstack-workflow/references/doc-templates docs/99-模板文档/
cp <本仓库>/templates/project-AGENTS.md AGENTS.md
```

然后把 `AGENTS.md` 里的「待补充」换成实际值：技术栈（带版本）、真实跑得通的命令、受保护分支名。**保持 100 行以内**——规则堆多了遵守率反而下降。

模块级规矩写在那个目录自己的 `AGENTS.md` 里，不要堆到根目录。`AGENTS.md` 是分层加载的：全局 → 项目根 → 子目录，全部合并。

### 2.6 装完怎么验

前四步机器能验，第五步只能人验。

```bash
# 1. agent：应为 8（1 主 + 7 角色，或多出旧版，需清理）
ls ~/.config/opencode/agents/ | wc -l                              # 8
grep -l "^mode: primary" ~/.config/opencode/agents/*.md   # 应有且仅有 fullstack-workflow.md
grep -c "mode: subagent" ~/.config/opencode/agents/*.md | grep -v ":0"   # 7 份

# 2. skill：应为 10（8 个 *-workflow + init-environment + init-project）
ls ~/.agents/skills/ | grep -c workflow   # 8
ls ~/.agents/skills/ | grep -c init-      # 2

# 3. 全局规则：9 个 ## 节题；门规则不在全局，在 agent 里
grep -c "^## " ~/.config/opencode/AGENTS.md     # 应为 9
grep -c "任务分级" ~/.config/opencode/AGENTS.md  # 应为 0（搬走才算对）
grep -c "四道门" ~/.config/opencode/agents/fullstack-workflow.md   # 应 ≥ 1

# 4. MCP 连上了
opencode mcp list | grep connected
```

**5. 最后两步只能人验**：

- 新开会话，agent 选 `fullstack-workflow`，说「改个错别字」→ 它应该拒收并让你切 `build`
- 再开一个，说「做个 X」→ 它应该先调 `init-project` 建骨架，再问清范围

**两句都对上，才算装好。**

### 2.7 重装与升级

| 情况 | 怎么做 |
|---|---|
| 完全没装 | 按上面全装 |
| 已有旧版（旧角色名） | 确认后删旧文件，再装新的 |
| **已装旧版 skill/agent** | **必须整套换**：旧 agent 是 7 个 subagent、没有主 agent；旧全局 AGENTS 有 12 节门规则。只补缺会两套并存 |
| 只想补缺 | 只拷缺的文件，**不覆盖已有的** |

不许盲目 `cp -r` 覆盖：手改过的配置会被冲掉。

**升级顺序**：先换 skill → 再换 agent → 最后换全局 AGENTS。反过来的话，`build` 会在中间那段时间里读到旧的门规则。

## 三、核心逻辑

这是本仓库最重要的部分。**装好只是把手装上，这一节决定它怎么动。**

### 3.0 先看全景：三个阶段、三次审查、四道门六个停点

**先选对入口。** 这套东西只有大任务才跑全程：

| 入口 | 级别 | 干什么 |
|---|---|---|
| `build` | 小 | 单文件、可一次回滚。改完说一句，不留 `docs/` |
| `plan` → `build` | 中 | 先出方案，人确认后再改。**方案在 plan 文件里，结果在 commit 里** |
| `fullstack-workflow` | 大 | 做项目、改数据结构、需迁移、上生产。整套 `docs/` + 七个角色 |

**级别由人选 agent 决定，不由模型自判。** 选错了由人切走——不设自动降级，也不许主 agent 自己把大事当小事做。

```text
阶段 1 · 设计与产品
  编排者问清范围 →【停点 1】人确认范围 → 原型（人提改到满意）
  →【停点 2】人确认原型 → 设计文档 → 产品文档
  → CR1 → 返修 →【门 1】人放行

阶段 2 · 架构与实现
  架构全套 → 架构自检 → TD
  →【门 2A】人确认方案（代码未写）
  → 代码 → 自测 → 实现记录
  → CR2 → 返修 →【门 2B】人验收

阶段 3 · 验证与发布
  测试全套（含真跑） → 运维全套
  → CR3 → 返修 →【门 3】人放行（两个问题）→ 上线
```

所以任何一步都可以这样问：**现在在哪个阶段？谁该交什么？交到哪？这个停点人答什么？**

| 谁 | 交什么 | 落点 | 卡在哪个停点 | 人答什么 |
|---|---|---|---|---|
| **编排者（你）** | 第一轮提问（不落文件） | 派发指令 → 设计 | **停点 1** | 范围、非目标、约束对不对 |
| 设计 | 原型（单 HTML）+ 设计系统 + 组件规范 | `docs/01-设计/` | **停点 2**、门 1 | 这些界面是不是实际要用的 |
| 设计 | 页面规格 | `01-设计/04-页面规格/01-<短名>_页面规格_v<版本>_<日期>.md` | **门 1** | — |
| 产品 | 需求池 + BRD + MRD + PRD + 术语表 | `docs/02-产品/` | **门 1** | 哪些不是我们的真实业务 |
| 审查 | CR1 | `docs/07-审查/02-审查报告/` | **不设门** | — |
| 架构 | 架构 + 图示 + 状态机 + 环境规范 + DB + ER + ADR | `docs/03-架构/` | **门 2A** | 表、状态、边界有没有漏/多 |
| 全栈开发 | TD（2A 前）→ 代码 + 实现记录（2B 前） | `docs/04-开发/`、`src/` | **门 2A / 2B** | 有没有你不知道的约束 / 实现符合方案吗 |
| 审查 | CR2（代码后） | `docs/07-审查/02-审查报告/` | **不设门** | — |
| 测试 | TP + TR | `docs/05-测试/` | **门 3** | 最怕出事的地方测到了吗 |
| 运维 | 服务详情 + 拓扑 + 手册 + 发布记录 | `docs/06-运维/` | **门 3** | 和真实环境一致吗 |
| 审查 | CR3 | `docs/07-审查/02-审查报告/` | **不设门** | — |
| 人 | 验收 / 上线 | — | **门 3** | 功能符合预期吗 / 现在就发吗 |

**计六个停点**：停点 1（范围确认）、停点 2（原型）、门 1、门 2A、门 2B、门 3。**只有门 1 / 2A / 2B / 3 写审查报告**，那两个停点只是「看一眼说可以」。

**三条推论，后面每一小节都在解释它们：**

```text
1. 每个角色都必须落文件。只回文字、零文件落盘的交付，等于没交（见 3.7 的 test -s）。
2. 产物在哪个路径是写死的，不是随手起名。路径就是身份（见 4.3 的整棵树）。
3. 门是串行闸门。上一次人没回话，下一个阶段就不能开始（见 3.8 的代价）。
```

### 3.1 第一步永远是选入口

**不是所有任务都值得走完整流程。** 让框架修一个拼写错误却产出四个用户故事、十六条验收标准，是这类框架被弃用的第一原因。

**级别不是一个「判断」，是一个「选择」。** 人选哪个 agent，就走哪一级：

| 入口 | 级别 | 判定 | 产物 |
|---|---|---|---|
| `build` | 小 | 单文件、不改数据结构、可一次回滚、不影响他人 | commit message + 一句说明 |
| `plan` → `build` | 中 | 多文件、跨模块，但不动 schema、不上生产 | plan 文件 + commit |
| `fullstack-workflow` | 大 | 做项目、改数据结构、需迁移、上生产、影响外部系统 | 整套 `docs/` + 七个角色 |

**中任务和小任务都产出东西，只是不落 `docs/`。** 中任务的方案在 plan 文件里，结果在 commit 里；只有大任务才建 `docs/` 那一套。**「不落 docs」不等于「不留痕」**——`git log` 就是中任务的档案。

**选错了怎么办：人手动停止，切走。** 不设自动降级，也不许 `fullstack-workflow` 自己决定「这个算小任务，我简单做」。它唯一的例外动作是**拒收**：明确说「这个适合 build / plan，请切换」。

### 3.2 大任务走完整条链

```text
编排者 → grill-me 问清范围（问到 frontier 空）                      →【人确认范围】
设计   → 原型（单 HTML，人提改到满意）+ 设计系统 + 页面规格
产品   → BRD + MRD + PRD + 术语表（读原型 + 派发问答，不读设计文档）
审查   → CR1（原型 ↔ 设计文档 ↔ 产品文档 交叉核对）
       → 返修（作者跑检查，不复审）                                  →【门 1】人放行

架构   → 架构 + 图示 + 状态机 + 环境规范 + DB + ER + ADR
       → 架构自检（PRD 每条规则有没有落点）
全栈   → TD（先落盘）                                           →【门 2A】人确认方案
       → 代码 → 自测 → 实现记录
审查   → CR2（PRD 规则 → 架构落点 → TD 路径 → 代码位置）
       → 返修                                                      →【门 2B】人验收

测试   → 测试策略 + TP（从 AC 反推）→ 真跑 → TR
运维   → 服务详情 + 拓扑 + 手册 + 发布记录
审查   → CR3（AC → TP → TR → 运维兜底）
       → 返修                                                      →【门 3】人放行
人     → 推代码，流水线部署
编排者 → 发布快照：本版产物搬进 docs/99-归档/发布/vX.Y.Z/
```

**中任务不走这条链。** 它用内置的 `plan` + `build`：

```text
plan（只读）→ 出方案，落 plan 文件 → 人确认 → 切 build → 改代码 → 自查 diff
```

中任务**不建 `docs/`、不派角色、不过门**。方案和结果都在 git 里。

### 3.3 四道门、六个停点

**门后必须是机器无法代判的内容。能机器判的不设门。**

**门 2 拆成两个停点**：方案（架构 + TD）在代码前先过人，代码写完过 CR2 再验收。**方案错在纸上改最便宜，代码写完再改要连测试一起返工。**

| # | 门 | 时机 | 先审吗 | 人只回答 |
|---|---|---|---|---|
| **1** | 设计与产品定稿 | 原型 + 设计系统 + 页面规格 + BRD/MRD/PRD/术语表，CR1 返修完 | **审（CR1）** | 这些界面、这些规则，**是不是我们要做的？原型缺了什么真实场景**？ |
| **2A** | 方案定稿 | 架构全套 + TD，**代码未写** | **不审（人直接看）** | 表、状态、边界**有没有漏掉真实存在的？有多出来的吗**？实施顺序有没有你不知道的约束？ |
| **2B** | 实现定稿 | 代码 + 实现记录，CR2 返修完 | **审（CR2）** | **实现符合方案吗**？**可以进测试了吗**？ |
| **3** | 验证与发布 | 测试全套 + 运维全套，CR3 返修完 | **审（CR3）** | **功能符合预期吗**？**现在就发吗**？ |

**2A 不设审查，是故意的。** 人在这道门判的是「有没有你不知道的约束」，不是技术对错；技术对错由 CR2 在代码后整条链核。**CR2 改动了架构或 TD 时，2A 必须重过**——方案变了，原来的方案确认就失效了；只改代码不用重过。

**另外两个不是门、但一样拦人的停点：**

| 停点 | 时机 | 人看什么 |
|---|---|---|
| **停点 1** | 范围问清，设计还没动 | 范围、非目标、约束对不对；有没有漏掉真实场景 |
| **停点 2** | 原型生成完，产品还没写 PRD | 这些界面是不是实际要用的；空态、错误态能不能接受 |

**这两个停点是产品写 PRD 的输入门槛。** 产品只读「人认可的原型」；原型没被认可就进产品，写出的规则要跟着返工。它们不写审查报告，不计入门，但人不说「可以」就不进下一步。

**门 3 是两个问题，不是一道门。** 只问「能发吗」，人会因为想快点上线而跳过功能核对。两个问题分开问，成本几乎为零，但保住了「验收」这个动作。

**这四道门的共同点：都不是「这东西好不好」，而是「这东西是不是真的」。** 好不好交给审查，真不真只有人说得出。

三条硬规矩：

```text
1. 人没说「过」，状态就是「待确认」，不进下游。没有「编排者代决」这条路径。
   推断、沉默、「你觉得呢」都不算。
2. 只有人能说「过」。文首的「放行」行由编排者代填，依据是人说过的那句话。
3. demo 的失败模式是「门由编排者代决」——门永远不能代决；
   非门事项（技术选型、命名、目录结构）可以代决，要留痕。
```

**门的顺序是「审查 → 人 → 通过」，不是「人看完直接过」。** 审查先把技术问题挑完，人看到的是已经审干净的版本——否则人会花时间在错别字和漏字段上，那是审查该拦的。

审查裁决不是「通过 / 有条件通过」时，**人这一关根本不启动**，产物直接回原作者。

### 3.4 审查：不设门，每个阶段审一次

审查回答「对不对」，不回答「是不是」。所以它没有自己的门，只当每道门的人的证据与抽查对象。

**三个阶段三次审查，是三个不同对象，不是同一份审三遍：**

| 审查 | 审什么 | 对照依据 | 核心工序 |
|---|---|---|---|
| CR1 | 原型 + 设计系统 + 页面规格 + BRD/MRD/PRD/术语表 | PRD + 原型 | **求差集**：PRD 说的页面 − 原型实际有 − 页面规格写了 |
| CR2 | 架构全套 + TD + 代码 + 实现记录（代码后，对应门 2B） | PRD | 规则链：PRD 规则 → 架构落点 → TD 路径 → 代码位置 |
| CR3 | 测试全套 + 运维全套 | PRD 的 AC + TR | AC 链：AC → TP 用例 → TR 结果 → 运维兜底 |

**「缺了什么」只能靠求差集，不能靠通读。** 通读只能看出「写了什么」，看不出「缺了什么」——**缺席不会自己喊。**

**没有「首审 + 复审」两轮制。** 审查出一次结论，每条阻塞项写成一条能跑的命令，作者改完自己跑，跑绿即算：

```text
P0-1 原型拆成了 15 个文件
  检查命令：ls docs/01-设计/03-原型图/*.html | wc -l
  期望：1　　当前输出：15　　状态：🔴
```

**「检查命令」这一栏不许写「检查一下 XX 有没有」。** 要写 `grep -c`、`ls | wc -l`、`diff`、`test -f`、`git log --format` 这类能跑出结果的命令。**人放行时只看有没有 🔴，全绿才进下一阶段。**

审查的自我约束：

| 约束 | 值 | 意义 |
|---|---|---|
| 单次审查时长 | 阶段 1 = 45 分钟 / 阶段 2 = 60 / 阶段 3 = 30 | **超时就停，写清审到哪**——超时硬审换来的是后半段质量下降，不是更多发现 |
| P0/P1 上限 | ≤ 15 条，超了判「退回重写」 | 15 条以上不是「有小问题」，是「还没想清楚」 |
| 代码 AC 抽样 | 30% 且 ≥ 10 条，缺陷率 > 20% 停下退回 | 抽样代替穷举，命中率就是信号 |
| 自检表 | 作者必须先交一张（清单项 / 结果 / 证据） | 审查第一道工序是验这张表，不是读产物 |

**自检表是入口，不是产出。** 作者照 `docs/07-审查/01-审查清单/01-审查清单.md` **第四节**里自己阶段那一小节逐项过一遍（4.1 阶段 1 / 4.2 阶段 2 / 4.3 阶段 3），留表交上来；表缺失、项数不够、证据是空的 → 直接退回。**清单里有、作者却填了 ✅ 的发现，算「自检造假」，比自检不足更严重。**

**这份清单由 `init-project` 在项目初始化时生成（9 节，无按角色分组那一节），必须在第一个角色交付前存在。** 清单缺席时，「照清单自检」客观不可执行。

### 3.5 产物：版本号是需求基线，不是修改次数

| 类 | 文档 | 文件名带版本 |
|---|---|---|
| **链上** | PRD、页面规格、系统架构、架构图示、状态机、数据库设计、ER 图、ADR、TD、实现记录、TP、TR、CR | ✅ 与整条链同版本 |
| **项目级** | BRD、MRD、术语表、设计系统、组件规范、需求池、环境规范、代码规范、测试策略、服务详情、部署拓扑、运维手册、发布记录、审查清单（共 14 份） | ❌ 不带版本，文首写「最后更新」 |

**同一条链上的版本必须全部相同。** 登记处只有一个：`docs/README.md` 的在途需求表。

**什么时候升版本：**

| 动作 | 升版本吗 |
|---|---|
| 新增 / 删除用户故事、功能 | **升** |
| 改业务规则（金额、权限、流程） | **升** |
| 改验收标准 AC | **升** |
| 修错别字、改表述、调格式 | 不升 |
| 补漏（需求本来就有，文档没写） | 不升 |
| **审查返修** | **不升** |
| 拆册 / 合册 | 不升 |

**判据一句话**：**「这条是不是原本就该有？」** 是 → 不升；不是 → 升。

**同一版需求内，改多少次都在原文件上改，版本号不动。** 变更记在产物的「变更历史」一节，只记日期和内容——**同一个版本号可以出现多行**。

**升版本时才走三步：**

```text
1. 链上全部产物一起拷到新版本号（一份都不能漏）
2. 内容真改的改内容；没改的只改文首版本行
3. 旧的一整套立刻搬进 docs/99-归档/版本/<需求>/<旧版本>/
```

**归档里一个版本一个目录，不合并。** 同一版本内的多次修改靠 `git log`，不靠目录。

**「写错了」不是升版本的理由。** 补漏、改表述、修错别字都留在同一版本，记进变更历史；只有需求基线变了才升。

**每份链上产物文首都有同一个三行头**，这是机器能查的唯一状态源：

```markdown
> **PRD1** · PRD · v1.3（**链版本**）· 20261120
> **审查**：待审查 | 已通过（CR1）| 有条件通过（未决 P2 N 条）| 退回修改
> **放行**：待确认 | 已放行 · <放行人> · <日期> | 未采信：零问询
```

| 行 | 谁填 | 什么时候 |
|---|---|---|
| `审查` | 审查角色（写 CR） | 阶段产物齐了才审；**三个阶段各一次** |
| `放行` | **人** | 审查裁决为「通过 / 有条件通过」之后 |
| `问询`（PRD） | 编排者 / 产品 | 轮次 N / 未回答 M / 代答 K，**N = 0 不许写「已放行」** |

**`已批准` 这个说法作废，统一叫 `放行`。** 「批准」可以指「我知道了」，`放行` 只指「可以往下走」。

### 3.6 返工：谁写的谁改，改完跑检查

| 情况 | 回给谁 | 怎么算改好 |
|---|---|---|
| 测试裁决「不通过」 | 写代码的人 | 同一问题 2 轮 |
| 审查裁决「退回修改」 | **写这份产物的人**：代码回开发、PRD 回产品、架构回架构、TD 回开发 | 跑审查给的检查命令，贴输出，全绿 |
| 审查裁决「退回重写」 | 同上 | 重写后重新走该阶段审查 |
| 改完仍不确定 | 编排者要求复审 | 只核阻塞项，不重读全文 |

**「谁写的谁改」意味着审查可以退回任何角色。** 退回后，那个阶段的门要重过——产物改过之后，人没看过的新版本不能进下游。

**返修只允许按审查意见改，不得顺手改别的。** 顺手改会让下一轮看不出改了什么。

### 3.6.1 并行：只有三处值得拆

**默认串行。** 只有同时满足三条才允许并行，缺一条就串行：文件不重叠、没有数据依赖、各自能独立验证。

| 环节 | 可拆几路 | 前提 |
|---|---|---|
| 架构出图（图示 / 状态机 / ER / ADR） | 3–4 | schema 与系统架构已定稿 |
| 开发（按模块） | 3–4 | TD 有分块表、共享面已冻结 |
| 测试执行（按测试层） | 2–3 | 每层独立库 schema |

**共享面必须在开工前冻结**：数据库表结构与迁移文件、接口签名、共享类型、共享组件 props。并行期间它们的 `git log` 必须为空；动了就要回门 2A。

**四道自保**：一路一个 worktree（独立端口、独立库 schema）· 只 `git add` 自己那一路的文件 · 交活跑越界自证 · 谁坏谁修（只回退坏的那一路）。

```bash
git worktree add ../wt-PRD<N>-W<k> -b feat/PRD<N>-W<k> dev
git diff --name-only dev...HEAD | grep -v "<自己的目录>" && echo "FAIL 越界" || echo "OK"
```

**冲突只有三种处置**：改同一文件 → 后交的那一路自己 rebase；有人动了共享面 → 全部停下、人拍板；某一路跑不通 → 只回退这一路。**不许编排者替 agent 解冲突，不许并发 `git commit`。**

**不能拆**：四道门、CR1/CR2/CR3、PRD 与 TD、迁移文件、`docs/README.md` 的在途表、发布。

### 3.7 子代理的报告只是声明

子代理回「已产出 N 个文件」，编排者必须在派发它的会话里当场验：

```bash
for f in <它声明的每个路径>; do
  test -s "$f" || echo "MISSING: $f"
done
```

任一文件不存在或为空 → 当作没产出，任务拆成「只写第一个文件」再派一次。**一次派发让子代理产出的文件数 ≤ 2。**

**验证要落成命令。** 把「验证」当口头要求会漏；`test -s` 每次都能给出同一结果。

### 3.8 门的代价

**这套门一旦落地，就不再支持「睡一觉让它跑完」。** 一个阶段交活 → 等人放行 → 下一个阶段才能开始，两次回话之间最多推进一个阶段（阶段 2 内部还多一个 2A 停点，代码不能越过它先写）。

代价是真实的：一次 12 小时无人值守换来的是「产品零提问、设计跑在门 1 之前、TD 写成事后归纳、ER 只画了 9/22 表」，全部要花一整个会话考古。**所以不设「预授权批量过门」的例外。**

## 四、日常怎么用

### 4.1 一次交付的典型走法

```text
1. 在项目里开一个会话，agent 选 fullstack-workflow
2. 说「按 PRD1 做」或「做个 X」
3. 它先问清范围，停下等你确认
4. 你确认后它派设计；原型出来再停下，你提改到满意
5. 之后每交完一个阶段就停下等人放行；你说「可以」，它才继续
```

**它不会自己定级。** 进了这个 agent 就是大任务；如果你在它里面只是改个错别字，它应该拒收并让你切到 `build`。

**人只回答一个问题**：这是不是真的。质量归审查，不归人。

### 4.2 说什么话触发什么 skill

| 你说 | 触发 |
|---|---|
| 「这个改动走什么流程」「下一步是什么」「该派谁」 | `fullstack-workflow` |
| 「写个 PRD」「需求不清楚」「要做个 X」 | `product-workflow` |
| 「出原型」「改界面」 | `design-workflow` |
| 「加张表」「要不要拆模块」「画架构图 / ER 图」 | `architect-workflow` |
| 「写技术方案」「开始实现」 | `develop-workflow` |
| 「写测试」「跑一下测试」「为什么挂了」 | `test-workflow` |
| 「审一下这个改动」 | `review-workflow` |
| 「部署」「写运维手册」「上线检查」 | `ops-workflow` |
| 「装工作流」「角色不见了」 | `init-environment` |
| 「新建项目」「建 docs 结构」 | `init-project` |

**团队分工时，每个人只装自己那个 `*-workflow`，但都要装 `fullstack-workflow`**——否则不知道自己现在站在门几。

### 4.3 产物落在哪：整棵目录树

**这个框架的本质就是三件事**：一个角色、一份落得下的产物、一道人过的门。所以产物目录是这套规范的骨架——**角色的产出物放在哪个路径、带不带版本、文件名怎么起，都是写死的**，不写死就会各写各的。

**一句话规则**：

```text
所有产物只在 docs/ 下，一处。按域分 01–07 七个目录。
链上的带版本，项目级的不带。登记处只有 docs/README.md 一个。
```

#### 4.3.1 项目根

```text
<项目根>/
├─ README.md                 # 项目是什么、怎么跑；新人第一个打开的
├─ AGENTS.md                 # 给 AI 的项目说明；模板见 templates/project-AGENTS.md
├─ .gitignore                # deploy/env/*（放行 .env.example）· docs/99-tmp/ · 其余三条
├─ .gitlab-ci.yml            # GitLab 只认根目录，放别处不执行
├─ src/                      # 源码 + 开发自写的单元测试（*.test.ts）
├─ test/                     # 按测试层分，编号即执行顺序
│  ├─ unit/                   # pure/（amount_test.ts）· components/（ProviderRow.test.tsx）
│  ├─ integration/            # api/（error_codes_test.go）· db/（invariant_test.go）
│  ├─ e2e/                    # flows/（register-flow.spec.ts）· visual/ · a11y/
│  ├─ perf/                   # scenarios/（chat-1000-mixed.js）；要压测才建
│  ├─ mobile/                 # flows/（login.yaml）；有 App 才建
```

```text
  03-架构/03-状态机/01-订单_状态机_v1.3.html
  03-架构/06-ER图/01-账号与商品_ER图_v1.3.html
```

**一个产物一个目录，文件名 `NN-<短名>_<类型>_v<版本>_<日期>.md`。** `NN` 是增补序号，不是版本号。

四条硬约束：

| 约束 | 说明 |
|---|---|
| **不使用 frontmatter** | 编号、版本、日期、状态一律写文首引用块前三行 |
| **链上产物全链同版本** | 升版本三步：整批 cp 到新号 → 改内容 → 旧的搬进 `99-归档/版本/` |
| **图目录里不建 `index.html`** | 图打开就是内容；要看「哪张图讲什么」，去归属文档的表格 |
| **`index.html` 只在 `03-原型图/`** | 全项目唯一例外，且它要么是原型本身，要么是多端时的导航页 |

**扩展名白名单**：业务目录的叶子层只放 `.md`；图目录（`03-架构/02-架构图示/`、`03-状态机/`、`06-ER图/`、`06-运维/02-部署拓扑/`）**只放 Archify 产物 html，不许 `.json`**；Archify 的收据统一进 `99-tmp/<角色>-<任务>/03-receipts/`。

#### 4.3.5 归档：有效的判据是位置，不是状态字段

| 目录 | 放什么 | 什么时候进 |
|---|---|---|
| `99-归档/版本/<需求>/<旧版本>/` | 被新版替代的整条链 | 链版本一升 |
| `99-归档/废弃/<需求>/<版本>/` | 整条需求被取消 | 需求不做了 |
| `99-归档/发布/<上线版本>/` | 一次上线的整批快照 | 真上线 |

**在工作目录里就是有效，在 `99-归档/废弃/` 里就是废弃。** 状态字段会忘记改，位置不会说谎。

**归档只进不出。** 要恢复旧版，正确做法是 `cp` 出来当新版本升号，不是搬回去顶替当前版。

**五棵树的完整结构只有一处权威：`skills/fullstack-workflow/references/project-layout.md`**（`init-project` 会把它复制到项目的 `docs/99-模板文档/`）。**它只写目录，不写规则。** 版本怎么升、分支怎么分、扩展名白名单、多图归目录的阈值——规则都在本文 §3.5、§4.3.4、§4.4 与 `doc-templates/*` 里，改规则改这里，不要改目录树那份。

### 4.4 分支策略

| 分支 | 推什么 | 为什么 |
|---|---|---|
| `dev` | 全量，含 `99-归档/` | 开发本地仓库，信息必须对等 |
| `test` | 只推当前版本 + 当次需要的产物，不含归档 | 测试环境只跑当前这套，冗余拖慢流水线 |
| `prod` | 只推运行需要的内容 + 当次发布快照 | 生产最小化，减少误操作面 |

**`test` / `prod` 只有人能合，AI 最高推到 `dev`。**

### 4.5 测试分两段

| 阶段 | 谁跑 | 跑什么 | 在哪 |
|---|---|---|---|
| 开发自测 | 全栈开发 | 单元 + 组件 + 类型 + lint | 本地 `dev` |
| 独立验证 | 测试角色 | 全量 + e2e | 本地先跑通，合进 `test` 后 CI 再跑，**报告以 CI 为准** |

两段都要过。本地过了不代表 CI 能过（环境差异），CI 过了也不代表测对了（用例可能没覆盖）。

### 5.1 OpenDesign（设计角色出原型）

官方 `od mcp install opencode` 生成的配置**不能直接用**，有两个坑：`od` 在 macOS 上被 `/usr/bin/od`（八进制 dump）占住；daemon 端口随机，不一定是 7456。

```bash
# 1. 打开桌面版，daemon 必须开着
open -a "Open Design"

# 2. 查实际端口
lsof -nP -iTCP -sTCP:LISTEN | grep -i design
```

```jsonc
// 3. 写进 ~/.config/opencode/opencode.json 的 mcp 段
"open-design": {
  "type": "local",
  "command": [
    "/Users/<你>/.local/bin/node",
    "/Applications/Open Design.app/Contents/Resources/app/prebundled/daemon/daemon-cli.mjs",
    "mcp",
    "--daemon-url", "http://127.0.0.1:<上一步查到的端口>"
  ],
  "enabled": true
}
```

**三个必须**：`node` 用绝对路径、`daemon-cli.mjs` 用绝对路径、`--daemon-url` 写真实端口。少一样就连不上。**端口每次重开桌面版都可能变**，连不上先重查端口。

### 5.2 Archify（架构与运维出图）

skill + Node CLI，不是 MCP。`npx skills add` 那一步**源必须写 `https://archify.si`**（带 https，走 well-known 端点只拉 skill 本体）；写成 `archify.si` 会被当 git 仓库去克隆，直接报 `repository does not exist`。也不要写 `tt-a1i/archify`——仓库 141 MB，大概率超时。

```bash
node ~/.agents/skills/archify/bin/archify.mjs doctor   # 20 多项全 [ok] 才算装好

node ~/.agents/skills/archify/bin/archify.mjs finalize architecture \
  candidate.json 02-架构图示.html --quality showcase --json \
  --out-dir docs/99-tmp/架构-<任务>/03-receipts/
```

四条硬约束：

| 约束 | 值 |
|---|---|
| 节点数 | **8–12 个**，超过就拆图 |
| 表数（ER） | 一张 **8–12 张表**，超过就拆图 |
| 画布宽 | ≤ 1240px（宽高比 ≥ 1.55 时可到 1790px） |
| 收据位置 | `--out-dir` 指到 `99-tmp`，**不许落在业务目录** |

**一次 `finalize` 只能出一种图。** 架构、状态机、ER 是三个独立文件——`meta.views` 只是同一张图的聚焦切换，不是把两种图拼一起。**流程时序图仍然用 Mermaid 写在 `01-系统架构.md` 里**：它数量多、改得勤、要对着读，做成 HTML 不划算。

**校验过了不等于图好看。** 过了还要看返回里的 `visualReviewRecommendation`，有交叉连线就按 hints 调坐标重跑，最多两轮。

## 六、常见问题

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 角色装上了但调不出来 | 缺 `mode: subagent`，或 `model` 还是占位 | 补 frontmatter，重启 |
| 机器上有 14 个角色，派错人 | 新旧两套名字并存 | 确认后删旧名文件 |
| 主 agent 自己把活干完了 | `description` 太笼统 | 写清「什么时候用」 |
| 技能不触发 | `description` 与任务不匹配 | 改 description，写清触发场景 |
| 该用的技能不在表里 | 表只覆盖常用 | 让它用 `find-skills` 现找。**注意 `code-review`、`find-skills` 不一定装了**，没装就走内置工具 |
| MCP 显示 needs authentication | 远程 server 要 OAuth | 会话里跑 `/mcps` 登录 |
| 子代理读不到文件 | 路径写成了相对当前目录 | 一律用项目根开始的相对路径 |
| 一次派了多个角色 | 没读到「一次只派一个环节」 | 确认全局 `AGENTS.md` 装的是本仓库 `templates/AGENTS.md` |
| `AGENTS.md` 装完少了分级和门的规则 | 装的是旧版（12 节，门规则塞在全局） | 重新 `cp templates/AGENTS.md`；验 `grep -c "^## "` = **9** |
| `AGENTS.md` 里写「三道门」「八道门」或「任务分级」 | 门规则被塞进了全局 | 用 `templates/AGENTS.md` 覆盖；验 `grep -c "^## "` = 9 且搜不到「任务分级」 |
| 睡一觉让它跑完，早上全是返工 | 门必须人过 | 不设预授权批量过门，见 3.8 |
| OpenDesign 连不上 | daemon 端口变了，或没开桌面版 | 重查端口改 `--daemon-url` |
| Archify 报 clone timeout | 没走代理，或源写成 `archify.si` | 导出 `https_proxy`；源写 `https://archify.si` |
| Archify 图不好看但校验全过 | 有交叉连线没修 | 看 `visualReviewRecommendation` 的 hints，调 `pos` 重跑 |
| 部署拓扑报 `deployment-private-state` | 数据库没放进 security-group | 每个环境建一个私网安全组，包住应用 + 数据库 |
| 部署拓扑报 `deployment-crossing-mechanism` | 连线 label 太笼统 | 写成「协议 + 端口 + 路径」，如 `HTTP 8080 轮询` |
| ER 图报 `references unknown entity` | `references` 写成了表名 | 用 entity 的 `id`：`"user.id"` 而不是 `"users.id"` |

## 八、活版本与备份

**活版本就是本仓库根目录下的 `skills/`、`agents/`、`templates/`。** `backup-docs/` 是它们的合订本，便于整体通读；**改了活版本要同步过去，那里改了不算生效。**

产物文件名里的 `vX.Y.Z` 是**链版本**（需求基线），与本文无关，见 4.3.4。
