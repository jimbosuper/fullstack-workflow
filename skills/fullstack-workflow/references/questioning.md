# 提问协议：把人说的话问清

**这份只讲「怎么问」。** 问完之后**不落文件**——问答随派发指令带进设计角色，PRD 承接范围与约束。

**谁问**：编排者在阶段 1 第 0 步问第一轮；产品看完原型补问第二轮。

---

## 一、为什么问完了不落文件

**范围不单独建档，由 PRD 承接。** 问出来的三样东西各有归处：

| 问出来的 | 落到哪 |
|---|---|
| 本期做什么、不做什么 | PRD 第四节「非目标（本期不做）」 |
| 金额口径、权限边界、合规、时间点 | PRD 第六节「业务规则」 |
| 页面清单 | 派发指令 → 原型 → 页面规格 |

**所以问完之后，人确认的是「这几条对不对」**，确认完把结论写进派发指令（几十行），直接交给设计。

**不建独立的需求中间文档。** 多一次落盘、多一处版本、多一个会漂的地方，换不来任何下游收益。

---

## 二、怎么问：设计树，不用清单

需求不是「十个待确认项」，是一棵**决策树**：每个决策分出依赖它的子决策。按**轮**问，每轮只问「前置已经定下来」的那一批——这一批叫 **frontier**。

```text
决策 1（给谁用）
├─ 决策 1.1（要不要多店铺）        ← 只有 1 定了才能问
│  └─ 决策 1.1.1（看板是否按店铺拆）
└─ 决策 1.2（谁有审核权）

决策 2（本期不做什么）
└─ 决策 2.1（不做的那块要不要留接口）
```

**一轮 = 当前 frontier 的全部问题，一次问完。** 依赖还没定下来的问题属于后面的轮，不要提前问——提前问会基于猜测，答案要返工。

**每问必须带推荐答案，措辞让「是」等于采纳。** 人被问「A 还是 B」会累，被问「我建议 A，行吗」很快。

```markdown
❓ **Q1 多店铺维度**：本项目看板按平台维度 + 合计，订单与商品不挂店铺。
如果真实业务是同平台多店，数据范围、看板口径、权限都要加一维。

➡️ 建议不做。代价是同平台多店无法分开看数。
```

**先问范围、钱、权限、合规；文案和颜色排后面。** 前者错了整条链返工，后者错了改一行。

**事实是自己查的，不是人答的。** 代码里的枚举、校验、`git log`、已有 PRD 能查到的不问；查不到才问。

---

## 三、什么时候算问完

**终止条件是 frontier 为空，不是「问不出新的」。**

| 检查 | 通过 |
|---|---|
| 每个决策节点都问过，或被明确标成「假设」 | ✅ |
| 没有「凭猜测定下来」的分支 | ✅ |
| 没有「等后面再说」而没说清谁在什么时候定 | ✅ |

**三条全绿才叫问完。**

| 需求原文形态 | 能不能少问 |
|---|---|
| 一句话（「做个 X」） | **必须问**：给谁用、核心解决什么、本期不做什么 |
| 有具体功能清单 | 可少问，但**范围边界**必须问 |
| 已明确范围边界与非目标 | 可只问优先级与交付形态 |

**自己的基线不能替代人的回答。** 「本期范围我定了，是 A/B/C」是候选，不是已确认需求——标「假设」并写明未经确认。

---

## 四、两种模式，别混

| 模式 | 条件 | 怎么做 |
|---|---|---|
| **有问必答**（正常） | 人在场 | 每轮问完**等人回答**，不往下走；frontier 清了才派设计 |
| **人不在**（例外） | 人明确说「按推荐走」或授权代决 | 按推荐值写进派发指令并标 `待确认`，记下未答条数 |

**人在场时不许用第二种**——那是把「我问了」变成「我猜了」的常见借口。

---

## 五、第二轮：产品看完原型再问

**原型会暴露第一轮问不到的东西**：「这个按钮点了之后去哪」「删了能恢复吗」「空态能做什么」。**由产品补问，协议同上。**

**为什么不能一次问完**：原型出来前，人看不到界面，这类问题问不出具体答案。**先画出来再问，问的是具体的东西。**

补问的结论写进 PRD 第六、第七节（业务规则、验收标准）；PRD 文首「问询」行记**总轮次**（第一轮 + 补问轮次）。

---

## 六、完成检查

- [ ] 第一轮至少问过一次；一次都没问就派设计 → 派发指令是草稿
- [ ] 每个问题带推荐答案
- [ ] frontier 三条检查全绿
- [ ] 结论已写进派发指令，人确认过
- [ ] 「本期不做什么」至少三条，且每条写了「什么时候可能做」
- [ ] 约束写的是具体金额口径 / 权限边界 / 合规要求，不是「按规范来」
